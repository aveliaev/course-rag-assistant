# КТ3. Запуск RAG-бейзлайна B0

Нужны Git, Docker Compose, `uv` и доступ к API GigaChat с моделью GigaChat-3-Ultra. Задай `GIGACHAT_CREDENTIALS` в окружении или в локальном `.env` в корне репозитория. `uv` создаёт окружение Python 3.12 и устанавливает зависимости по lock-файлу с проверкой хешей.

В свежем клоне из корня репозитория выполни:

~~~sh
git fetch origin kt-2
./kt3/run_b0.sh runs/b0-kt3
~~~

Скрипт читает корпус из `tmp_dataset`, а dev-набор и профили из зафиксированного коммита КТ2 `6c56bcb`. Docker поднимает Qdrant на `127.0.0.1:16333` и PostgreSQL на `127.0.0.1:15432`. Первый запуск загружает модель эмбеддингов и собирает индекс на CPU. Это самый долгий этап. Обработка документов и эмбеддингов сохраняет прогресс в `kt3/.cache`.

После построения индекса скрипт использует [зафиксированную калибровку](infra/retrieval-calibration.json) с порогом 0,55, запускает тесты, семь диалогов, smoke обоих вариантов и три повтора dev для B0. Прогоны идут последовательно. Повтор той же команды с тем же кодом и конфигурацией продолжает сохранённый прогон. При ответе 429 можно продолжить его после восстановления квоты. Для изменённых настроек укажи новый каталог.

~~~sh
kt3/.venv/bin/fkn-ask --question 'Какая шкала оценивания принята в Вышке?'
~~~

Общий интерфейс `fkn-eval --variant ... --dataset ... --output ...` запускает `rag-b0`, `rag-b1`, `search-only` и `prompt-only`. B0 отвечает через GigaChat по найденному контексту. B1 добавляет модельный разбор намерения и вытаскивает дословные фрагменты полей, значения проверяет код. `search-only` использует тот же индекс и поля формы, для информационного ответа цитирует первый фрагмент. Ему достаточно Docker и построенного индекса, ключ GigaChat требуется B0, B1 и эксперименту с одним промптом. Для собственного запуска можно передать `--repo`, `--env` и `--ca`. Дополнительный эксперимент `prompt-only` описан в [первом отчёте](docs/results.md).

- `dev/run.json` хранит параметры и версии, хеши кода, набора, профилей и источников.
- `dev/responses/` содержит ход приложения, ответ модели, переданные выдержки, автоматические проверки, выдержку из журнала действий, токены и задержку.
- `dev/summary.json` и `results-rag.md` содержат сводку. `dev/review.json` и `dev/review.md` содержат 50 примеров для ручной проверки.
- `dialogues/dialogues.json` содержит семь последовательностей, шаги, ответы и выписку из базы по каждому ходу.

Подготовка `search-only` без доступа к API генерации, из корня после `git fetch origin kt-2`:

~~~sh
uv venv --python 3.12 kt3/.venv
uv pip sync --require-hashes --python kt3/.venv/bin/python kt3/infra/requirements-lock.txt
uv pip install --python kt3/.venv/bin/python --no-deps --editable ./kt3
docker compose -f kt3/infra/compose.yaml up -d --wait
kt3/.venv/bin/fkn-index
cp kt3/infra/retrieval-calibration.json kt3/.cache/retrieval.json
~~~

Из корня репозитория после построения индекса:

~~~sh
kt3/.venv/bin/fkn-eval --variant search-only --dataset dev --repeats 1 --output kt3/runs/search-only
kt3/.venv/bin/fkn-eval --variant rag-b1 --dataset dev --repeats 3 --output kt3/runs/b1
kt3/.venv/bin/fkn-report kt3/runs/b0-kt3/dev --compare kt3/runs/b1
~~~

Для проверки проводки B1 через CLI с фикстурой модели и настоящими локальными хранилищами:

~~~sh
kt3/.venv/bin/python kt3/tests/run_b1_fixture.py --output kt3/runs/b1-fixture-smoke
~~~

Парный отчёт берёт только первый повтор, сверяет хэши dev, профилей и индекса, сообщает изменения автоматических метрик. Для обоих вариантов используйте один снимок поиска и те же калибровку и параметры модели ответа. В отчёте B1 отдельно сохраняется промпт разбора намерения. Проверка с поставщиком-фикстурой подтверждает сценарий исполнения, оценка качества требует живого GigaChat.

## HTTP-шлюз учебной песочницы

[OpenAPI 3.1](infra/sandbox.openapi.yaml) фиксирует контракт запроса форм, предпросмотра тикета учебного офиса и подтверждения. Поднимите PostgreSQL через Compose. Перед запуском установите в окружении случайный `KT3_SANDBOX_TOKEN` с длиной от 24 символов и передавайте его доверенным клиентом как Bearer. Затем из корня запустите:

~~~sh
kt3/.venv/bin/python -m fkn_assistant.sandbox_api
~~~

Шлюз доступен по loopback на 18083. Профиль выбирает доверенный тестовый клиент из синтетических данных. Для заявки можно передать реплику, затем отдельное событие кнопки с версией карточки. Для учебного офиса сначала запрашивается карточка E1–E4, клиент показывает её сводку, затем отдельным подтверждением создаёт запись в PostgreSQL. Повтор подтверждения возвращает тот же ID. Автоматический вызов этой операции из разговора и связь с учебным офисом относятся к решению команды по §11.

## Структура

- `src/fkn_assistant/` содержит runtime, поиск, проверку ответов и формы.
- `providers/` внутри пакета содержит адаптер GigaChat, `resources/` — промпты, правила и сертификат.
- `evaluation/` внутри пакета содержит харнесс, сценарии, метрики и отчёты.
- `infra/` содержит Docker Compose, lock-файл и зафиксированную калибровку.
- `docs/`, `tests/` и `evidence/` содержат документацию, тесты и артефакты измерения.

## Рубрика ручной проверки

Два участника независимо оценивают 10 кейсов с пометкой «Двойная проверка». До сохранения первичных оценок используйте review.md и эту рубрику, открывайте файл оценок Codex после независимого этапа. Затем сравнивают разметку, уточняют спорные правила, фиксируют исходное согласие и проходят оставшиеся кейсы. Эталонную рубрику применяют по фактически выбранному допустимому статусу. Отдельно записывают:

1. **Исход и смысл.** Уместен ли ответ, отказ или уточнение, есть ли обязательные факты или поля, нет ли существенных ошибок. Названные в эталоне запрещённые действия и утверждения проверяются отдельно.
2. **Документ и ПУД.** Есть ли применимый источник, подтверждает ли он конкретное утверждение, относится ли к фактическому периоду изучения. Явное уточнение периода или потока допустимо в соответствующих кейсах. Ссылки без подтверждения исходным документом не засчитываются. Отсутствие существенных утверждений означает «неприменимо» для полноты цитирования.
3. **Формы.** Для пропуска и справки отдельно сверяют значения, пропуски и источник полей. Проверяют, что ответ не заявляет об отправке. Подтверждение и отмена измеряются отдельными последовательностями КТ3.
4. **Метки.** По каждому применимому критерию ставят `pass`, `fail` или `not_verifiable`. Для неприменимого — `n/a`. Записывают ID кейса и конкретную причину ошибки. Для итогового успеха нужен `pass` по всем применимым условиям контракта. Публикуют числитель, знаменатель и число непроверяемых примеров отдельно.

Автоматические метрики измеряют совпадение структуры с эталоном. Полное выполнение контракта требует смысловой проверки. Результат ручной выборки относится к выбранным примерам, а показатели форм считаются раздельно из-за малого покрытия. Отдельные токены оценки моделью не расходуются.

Отчёт из сохранённых результатов:

```sh
kt3/.venv/bin/fkn-report kt3/runs/b0-kt3/dev > kt3/runs/b0-kt3/results-rag.md
```

После ручной проверки добавь `--grades путь/к/разметке.jsonl`. Каждая строка содержит
`{"case_id":"ID","checks":{"outcome":"pass","evidence":"n/a","form":"n/a","safety":"pass"},"notes":"обоснование"}`.
`n/a` для evidence допустимо в кейсе без существенных утверждений, для form — в кейсе без заявки.
У каждого участника свой файл до сверки. Записи с `reviewer_kind: "ai"` учитываются отчётом отдельно от человеческой проверки. В отчёт передаётся итоговая разметка.

Читаемая копия пакета ручной проверки:

```sh
kt3/.venv/bin/fkn-report kt3/runs/b0-kt3/dev --review > kt3/runs/b0-kt3/dev/review.md
```

Согласие по исходным меткам двух участников, до объединения:

```sh
kt3/.venv/bin/fkn-report kt3/runs/b0-kt3/dev --agreement reviewer_a.jsonl reviewer_b.jsonl
```

Команда выводит число совпавших итоговых вердиктов, κ Коэна и ID кейсов, где расходится хотя бы один критерий.
