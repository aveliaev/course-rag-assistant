# КТ3. Сравнение на первом повторе dev

Оба запуска прошли через `fkn-eval` на одинаковых 148 ID, с одинаковыми хэшами профилей и корпуса, реестром, настройками поиска и порогом 0,55. У B0 берётся первый повтор сохранённого прогона, у `search-only` — один новый прогон. Формы и состояние общие. Информационный `search-only` отдаёт первый фрагмент с локатором после порога, а B0 использует GigaChat для ответа по найденным выдержкам.

У `search-only` 148/148 записанных ходов, 0 ошибок, 0 генераций и 0 ₽ расходов API генерации. Активная часть прогона заняла 14.61 с. Расходы на локальную инфраструктуру и подготовку индекса здесь не оцениваются.

Отметка hit@20 совпала на всех применимых кейсах. Hit@5 изменился на одном кейсе (E030). Порядок всех фрагментов совпал у 22/148, набор фрагментов без учёта порядка — у 127/148, первый фрагмент — у 121/148 (здесь учитываются также пустые выдачи в обоих вариантах). У ряда фрагментов равные оценки RRF, поэтому перестановки влияют на ответ выдержкой. Сравнение показывает поведение целых конфигураций. Чтобы оценить вклад одной генерации, нужен повтор на одних записанных выдачах.

B1 через тот же CLI прошёл smoke из 20 ходов с фиксированными ответами модели, с локальными Qdrant и PostgreSQL. Из них 9 прошли оба вызова, ошибок и неожиданных записей не было. Это проверка исполнения; качество и задержка B1 на GigaChat пока не измерены.
