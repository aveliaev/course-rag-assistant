Из 23 расхождений в опубликованном протоколе КТ2 14 приходятся на `not_verifiable` ↔ `pass`, ещё 9 — на `pass` ↔ `fail`. Из 50 случаев оценки применимости совпали в 32, поведения — в 33. Доступ к разным материалам и неоднозначность критериев — причины, отмеченные в документации. Для анализа каждого из 23 случаев нужны исходные файлы обоих участников и протокол. В дереве исторического коммита КТ2 доступны дизайн-док, dev, test и профили. [История оценки КТ2](https://github.com/aveliaev/course-rag-assistant/blob/6c56bcbcf06f6cba296bb9674a43bf6739887cc0/KT-2/design_doc_kt2.md)

**Проверить происхождение исторической оценки.** В §5.1.4 КТ2 строка «Илья» содержит 29 `pass`, 16 `fail`, 5 `not_verifiable`. Эти числа совпадают с прежним файлом, который Codex подготовил с полем `reviewer: "Илья"` (SHA-256 `86aa1ec795f979edfe655020b4b545afb2d6a98deac8d7d72499e63ff6a2d3a6`). Совпадение чисел не устанавливает происхождение. Сверьте исходный файл по SHA-256 или истории правок. Если для расчёта использован файл Codex, исправьте обозначение пары и пересчитайте согласие после двух независимых человеческих проверок.

Для повторной проверки обоим нужен один комплект: фиксированные источники по версии и локатору, данные программы и периода, одинаковая рубрика. Уточнить границы меток: `fail` при проверенном противоречии или пропущенном обязательном условии, `not_verifiable` при отсутствии данных для решения, `n/a` для неприменимого критерия. Сначала независимо разметить одинаковые ID, затем зафиксировать сырые оценки, долю совпадений и κ, после этого обсуждать расхождения. Исторический `test_152.jsonl` доступен в Git и имеет историю раскрытия. Для КТ4 назначить хранителя нового набора, отделить семейства вопросов от dev, закрыть доступ разработчикам и зафиксировать хэши до запуска.
